# Кешування, рендеринг, proxy

ADR: ADR-8, ADR-9, ADR-14, ADR-7

### ADR-8. Кешування й інвалідація

Первісна версія цього ADR була концептуально хибною: вона твердила, що
`updateTag` дає адмінці свіжість, а `revalidateTag` — вітрині «протягом
ревалідації». Це не два незалежні кеші. Якщо тег той самий, інвалідуються
ті самі записи, і різної свіжості не буде.

Виправлена модель:

**Адмінські читання не кешуються взагалі.** Контент-менеджер мусить бачити
власну правку негайно; це досягається відсутністю кешу, а не спеціальним API.

**Публічні читання кешуються явно.** Drizzle-запити самі собою не кешуються
нічим — при вимкненому `cacheComponents` (ADR-9) потрібна явна обгортка з
ключами по locale й параметрах фільтрів і з тегами `product:{id}`,
`category:{id}`. Простого SQL-запиту в server component недостатньо.

**Інвалідація вітрини — одна погоджена семантика:** `revalidateTag(tag, 'max')`
після мутації. Другий аргумент обов'язковий, форма з одним deprecated.

**`updateTag` доступний тільки в Server Actions** — і використовується тоді,
коли та сама дія мусить одразу віддати оновлений результат у тій самій
відповіді.

**`refresh()`** — оновлення клієнтського роутера з server action: лічильник
кошика, бейдж нових замовлень.

#### Воркер не може інвалідувати кеш Next.js

Це найважливіше практичне обмеження: `revalidateTag` живе всередині
Next.js-рантайму, а воркер — окремий процес. Тому зміна залишків або статусу
з воркера йде через `outbox` → захищений внутрішній endpoint інвалідації в
`apps/web`, який і викликає `revalidateTag`.

При зміні категорії товару інвалідуються **і стара, і нова** категорія.

### ADR-9. `cacheComponents` (PPR) — НЕ вмикаємо у v1

У 16 експериментальний прапор PPR прибрано, замість нього top-level `cacheComponents`. Документація прямо попереджає: це не перейменування, воно ламає білд на будь-яких некешованих даних поза `<Suspense>` і вимагає прийняти модель Cache Components цілком.

Рішення: v1 їде на звичайному ISR. `cacheComponents` розглядаємо як окрему міграцію після запуску, коли є що міряти.

Так само **React Compiler** (`reactCompiler: true`) — стабільний, але вимкнений за замовчуванням і працює через Babel, тобто збірка сповільнюється. Вмикати тільки якщо профайлер покаже проблему з ре-рендерами, а не «бо є».

### ADR-14. `proxy.ts` не ходить у БД на кожному запиті

`proxy` виконується перед кожним запитом. Читання таблиці `redirects` з
Postgres звідти означає запит до БД на кожен перегляд сторінки — і будь-який
сканер вразливостей або сплеск трафіку вичерпує пул з'єднань і кладе сайт.

Рішення:

1. **Жорсткий `matcher`**: лише потрібні GET/HEAD-маршрути вітрини. Виключити
   `/_next/*`, статику, зображення, `/api/*`, вебхуки, адмінку.
2. **Кеш редіректів у пам'яті процесу**: `Map<fromPath, {toPath, status}>`,
   завантаження **single-flight** (паралельні запити при холодному кеші не
   породжують N запитів до БД), TTL 60 с. Таблиця мала — тримати її цілком у
   пам'яті дешевше за будь-який запит.
3. **Stale-on-error**: при тимчасовій помилці БД використовується остання
   справна карта, а не 500 на всю вітрину.
4. Інвалідація при зміні slug — через `settings.redirects_version`; TTL
   лишається страховкою від пропущеного сигналу.
5. Префікс-фільтр — **скорочення області перевірки, не заміна кешу**.
6. `hit_count` інкрементується **асинхронно** через outbox, не в проксі.

Кеш живе в межах інстансу. Dokploy може підняти кілька контейнерів — TTL
забезпечує сходження за хвилину, що для редіректів прийнятно.

Аргумент «Node runtime тепер дозволяє Postgres» описує технічну можливість, а
не виправдання: сам Next.js окремо застерігає від повільного fetching у proxy,
бо він виконується перед маршрутизацією, тобто навіть перед кешованою
сторінкою.

### ADR-7. Стан фільтрів — URL

Query-params — єдине джерело істини для PLP. Ніякого дублювання в стані клієнта. Дає шеринг посилань, кнопку «назад», індексацію й серверний рендер без гідратаційних розбіжностей.
