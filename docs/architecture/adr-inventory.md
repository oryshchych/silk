# Склад, резервації, локи

ADR: ADR-3, ADR-18, ADR-22

### ADR-3. Резервації замість прямого списання

```
available = stock_quantity - reserved_quantity
```

При створенні замовлення — запис у `stock_reservations` з `expires_at` і
атомарний інкремент `reserved_quantity`. При оплаті — резервація знімається,
`stock_quantity` зменшується. При скасуванні або протермінуванні (воркер) —
резервація знімається без зміни `stock_quantity`.

**TTL залежить від методу оплати.** Єдиний TTL на 72 години був помилкою: він
відкриває вектор, у якому серія фейкових замовлень з післяплатою вимиває
популярні розміри на три дні, і магазин простоює без продажів.

| Метод | TTL | Обґрунтування |
|---|---|---|
| Картка (mono, WayForPay) | 30 хв | Стільки живе платіжна сторінка. Не оплатив — резерв вільний |
| Банківський переказ | 24 год | Реальний час зарахування |
| COD (післяплата) | **2 год** до підтвердження менеджером; після підтвердження — до `shipped` | Найризиковіший метод: гроші не заблоковані нічим, тому вікно до підтвердження мусить бути коротким |

Значення — у `settings.reservation_ttl`, не в коді, бо їх доведеться крутити за
реальною статистикою відмов.

Додатково для COD, бо TTL сам по собі не захищає від наполегливого бота:
rate limit по парі (телефон, IP), ліміт незавершених COD-замовлень на телефон,
чорний список телефонів із історією відмов при отриманні.

`reserved_quantity` денормалізований, щоб не рахувати суму резервацій на
кожному читанні PLP. Воркер щогодини звіряє денормалізоване значення з
реальною сумою і **алертить** при розбіжності, а не виправляє тихо.

Атомарність:

```sql
UPDATE product_variants
   SET reserved_quantity = reserved_quantity + $2
 WHERE id = $1
   AND stock_quantity - reserved_quantity >= $2
RETURNING id;
```

Нуль рядків → товару немає → транзакція відкатується. Ніяких `SELECT` перед
`UPDATE`, ніякої перевірки в застосунку.

### ADR-18. Семантика складу: одна, однозначна

Попередня версія містила три взаємно несумісні правила: TTL резервації per
method, `expires_at NOT NULL` у схемі, списання `stock_quantity` при `paid` і
воркер, що скасовує все неоплачене. COD-посилка на четвертий день дороги
призводила до звільнення резерву й повторного продажу фізично відправленої
одиниці.

Єдина семантика:

| Поняття | Значення |
|---|---|
| `stock_quantity` | **фізичний залишок на складі.** Зменшується тільки при `shipped` |
| `reserved_quantity` | зобов'язання перед покупцями. Тримається **до відправлення**, не до оплати |
| `available` | `stock_quantity − reserved_quantity` |

Переходи:

- **Створення замовлення** → резерв, `expires_at` за TTL методу оплати
- **Оплата (`paid`)** → резерв **не звільняється**, `expires_at := NULL`
- **Підтвердження COD менеджером** → `expires_at := NULL`
- **`shipped`** → одним переходом: `stock_quantity -= q` і `reserved_quantity -= q`, резерв закривається з `release_reason = 'shipped'`
- **Скасування / протермінування** → резерв закривається, `stock_quantity` **не змінюється**
- **Фізичне приймання повернення** → `stock_quantity += received_quantity`

Три терміни розведені й не є синонімами: `release reservation`, `ship stock`,
`receive return`. Первісний план казав «повернення на склад при `failed`» —
агент реалізує це літерально й отримає `stock = 2` там, де товар лише
резервувався.

Звільнення резерву — **умовний перехід**, щоб воркер expiry й вебхук не
звільнили один резерв двічі:

```sql
UPDATE stock_reservations
   SET released_at = now(), release_reason = $2
 WHERE id = $1 AND released_at IS NULL
RETURNING quantity;
```

`reserved_quantity` зменшується **тільки на фактично змінені рядки**, у тій
самій транзакції.

**Відмова від COD:** повернення йде **з `shipped`**, без фіктивного
`delivered`. Поповнення складу — після фізичного приймання, не після
переходу статусу.

**Пізня оплата після expiry** записується як фінансовий факт завжди, навіть
якщо товару вже немає. Замовлення переходить у явний винятковий стан для
менеджера. Не відкидати платіж і не дозволяти відправлення автоматично.

### ADR-22. Порядок узяття блокувань — один, глобальний

З'явився як наслідок правок за рецензіями: тепер у проєкті **чотири** типи
рядкових блокувань, які можуть перетинатися в одній транзакції.

| # | Об'єкт | Коли |
|---|---|---|
| 1 | `carts` | **будь-яка** мутація кошика блокує батьківський рядок першим |
| 2 | `checkout_intents` | оформлення, перезапуск |
| 3 | `orders` | обробка вебхука, зміна статусу, редагування складу |
| 4 | `order_items` | повернення, часткове приймання — **за зростанням id** |
| 5 | `payment_attempts` | повернення коштів, звірка статусу |
| 6 | `promo_codes` | застосування й звільнення використання |
| 7 | `gift_cards` | погашення, повернення на сертифікат |
| 8 | `product_variants` | резервування, списання, поповнення — **за зростанням id** |

**Локи беруться строго в цьому порядку.** Транзакція, яка потребує кількох,
бере їх від меншого номера до більшого й ніколи навпаки.

Приклад, де це критично: створення замовлення бере `promo_codes` (3) і
`product_variants` (5); скасування замовлення бере `orders` (1),
`promo_codes` (3) і `product_variants` (5). Якщо один шлях візьме промокод
перед замовленням, а інший — навпаки, ви отримаєте deadlock, який
відтворюється раз на кілька сотень замовлень і не ловиться тестами, що
виконуються послідовно.

Тому: у `packages/core` є єдина функція `acquireLocks(tx, spec)`, яка
сортує запит і бере локи в правильному порядку. Прямі `SELECT ... FOR UPDATE`
у доменному коді — заборонені лінт-правилом.

**Три уточнення, без яких протокол не працює:**

1. **Повний набір визначається до першої мутації.** Сортування всередині
   одного виклику `acquireLocks` не гарантує порядок між **кількома**
   викликами в тій самій транзакції. Тому helper веде облік уже взятого
   рівня й **відхиляє** спробу взяти нижчий — це перетворює порушення
   протоколу з рідкого deadlock у детермінований виняток на етапі розробки.
2. **Тригери й звичайні `UPDATE`/`DELETE` теж беруть локи**, навіть без
   тексту `FOR UPDATE`. Зокрема тригер інкременту `cart_version` бере лок на
   `carts` при зміні `cart_items` — тому мутація кошика мусить блокувати
   батьківський рядок **першою**, інакше отримуємо deadlock із checkout,
   у якому всі явні `FOR UPDATE` пройшли через дозволений helper.
3. Сортування за id — у межах **кожного** типу окремо, не глобально.

Тест обов'язковий: два конкурентні шляхи з перетинними локами в різному
логічному порядку, з окремих з'єднань і з бар'єром синхронізації. Плюс
окремий тест на локи, породжені тригерами.
