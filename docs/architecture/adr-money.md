# Гроші, знижки, фіскалізація

ADR: ADR-1, ADR-15, ADR-16

### ADR-1. Гроші — `integer` копійки, з явною точкою округлення

Усі суми — цілі числа в копійках. `1299.00 ₴` → `129900`.

**Обґрунтування виправлено.** Первісно тут стояв аргумент через
`0.1 + 0.2 !== 0.3` — він некорректний як аргумент проти PostgreSQL
`numeric`, бо `numeric` є точним десятковим типом. Реальні причини вибору
integer: арифметика без коштів на decimal-обгортки в JS, однозначна
серіалізація в JSON без втрати точності, і те, що для UAH без дробових
копійок ширшої точності не потрібно.

**Правило «округлення один раз, при відображенні» також було
неправильним.** Воно несумісне з відсотковими знижками: 15% від 19 999
копійок — це 2 999,85 копійки, і рішення потрібне **до запису**, а не в UI.

Виправлене правило:

1. Точка округлення — **pricing engine**, `packages/core/pricing`. Не UI, не БД.
2. Проміжні множення виконуються точно; округлення відбувається один раз на
   рівні позиції, і залишок розподіляється детерміновано (ADR-15).
3. Розподіл зберігається в `order_items.line_discount` — не перераховується
   при кожному читанні.
4. Перед записом перевіряється діапазон `integer` (максимум ≈ 21 млн ₴ на
   значення).
5. Явно зафіксовано: **`subtotal` НЕ включає `line_discount`**, тобто
   `subtotal = SUM(line_total + line_discount)`. Без цього легко відняти ту
   саму знижку двічі.

`packages/shared/money.ts` — типи-обгортки, форматування і функції
розподілу. Ніяких «сирих» чисел у доменних сигнатурах.

**Чого branded type НЕ дає.** `Money` — підтип `number`, тому `money(100) / 3`
компілюється, і `multiply(m, 0.15)` створює нецілий `Money`, якщо функція
робить assertion без перевірки. Brand забороняє лише передати сирий `number`
туди, де очікується `Money`. Заборона операторів вимагає окремого
лінт-правила, кожна операція повертає результат через конструктор із
`Number.isSafeInteger`, а відсотки — окрема функція з явним округленням.
Деталі в `DEVELOPMENT.md` §2.

### ADR-15. Розподіл знижки по позиціях, а не тільки на замовлення

Знижка зберігається **і** на замовленні (`discount_total`), **і** розкладена по
позиціях (`order_items.line_discount`). Друге обов'язкове, бо без нього не
сходяться копійки.

Приклад: знижка 100 ₴ на три позиції по 200 ₴ дає 33,33 ₴ на позицію, сума
ліній — 99,99 ₴. Розбіжність в одну копійку між сумою позицій і сумою
замовлення ламає фіскальний чек (ПРРО відхиляє) і часткове повернення.

Алгоритм — **largest remainder**, і перша редакція описувала його
неправильно: там було «залишок копійок додати до найдорожчої позиції». Це
не largest remainder, і воно дає знижку, більшу за ціну позиції.

Контрприклад, відтворений рецензією: ціни `1000, 999, 998`, знижка `2996`.
Пропорційно з округленням вниз — `999, 998, 997`, разом 2994, залишок 2
копійки. Додавання обох до першої позиції дає знижку `1001` при ціні `1000`,
тобто `line_total = −1`. Коректний `CHECK` відхиляє цілком легітимну акцію.

Правильно:

1. Порахувати ідеальну частку кожної **eligible**-позиції, взяти floor.
2. Залишок роздати **по одній копійці** позиціям із найбільшою дробовою
   частиною, у порядку спадання; tie-breaker стабільний (за `id`), щоб
   результат був детермінованим і відтворюваним у тестах.
3. Після розподілу перевірити `line_discount <= line_subtotal` для кожної
   позиції. Якщо не сходиться — це баг алгоритму, не дані.

Реалізація в `packages/core/pricing/allocate-discount.ts`. Наведений
контрприклад — обов'язковий тест-кейс. Той самий детермінований розподіл
застосовується при часткових поверненнях, усередині кількості позиції.

Інваріант `discount_total = SUM(line_discount)` та
`subtotal = SUM(line_total + line_discount)` **не виражається як `CHECK`** —
це cross-table. Тримається транзакцією в `core` плюс запитом-звіркою у
воркері `orders:reconcile-totals`, який алертить про розбіжності.

### ADR-16. Фіскалізація ніколи не блокує підтвердження платежу

Прив'язка до відкритого питання №1 (`PLAN.md`).

Порядок жорсткий: вебхук підтвердив оплату → замовлення `paid` → **окрема
задача в чергу** на пробиття чека. Не навпаки.

Причина: якщо пробивати чек синхронно в обробнику вебхука і ПРРО віддасть 503,
у вас два погані варіанти — або відкотити транзакцію (гроші в еквайрі є, а
замовлення `pending`), або зафіксувати оплату без чека, але вебхук уже
відповів помилкою і провайдер ретраїтиме.

Тому:
- Чек — задача pg-boss з експоненційними ретраями.
- Після N невдач — алерт у Telegram і статус `fiscal_status = 'failed'` на замовленні.
- Екран в адмінці «замовлення без чека» з кнопкою ручного повтору.
- Розбіжність між еквайрингом і фіскальними чеками звіряється щодня воркером.

`FiscalProvider` — той самий патерн, що `PaymentProvider`: інтерфейс плюс
реалізація, вибір у `settings`.
