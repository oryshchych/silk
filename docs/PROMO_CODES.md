# PROMO_CODES.md

Адаптація документації промокодів з проєкту реєстрації на івенти під цей
магазин. Стек інший (Postgres + Drizzle замість Mongo, server actions замість
Express-контролерів), і три рішення оригіналу змінені свідомо — див.
«Відхилення від оригіналу».

**Промокод — це не подарунковий сертифікат.** Різниця — в `GIFT_CARDS.md`.
Коротко: промокод зменшує ціну, сертифікат є способом оплати. Плутати їх
означає задвоїти виручку в звітах.

---

## 1. Модель даних

Таблиця `promo_codes` у `schema.ts`. Відповідність полів оригіналу:

| Оригінал (Mongo) | Тут | Примітка |
|---|---|---|
| `code` | `code` | unique по `upper(code)`, не по сирому рядку |
| `discountType: 'percentage' \| 'amount'` | `type: 'percent' \| 'fixed' \| 'free_shipping'` | додано безкоштовну доставку — для магазину це третій за популярністю тип |
| `discountValue` | `value` | для `fixed` — **копійки**, не гривні (ADR-1) |
| `usageLimit` / `usedCount` | `max_uses` / `uses_count` | `max_uses = NULL` означає без обмежень |
| `isActive` | `is_active` | |
| `expirationDate` | `starts_at` / `ends_at` | додано початок дії: акції планують заздалегідь |
| `eventId` | `scope` + `scope_category_id` / `scope_product_id` | івент → категорія або товар |

Додано, чого в оригіналі не було і без чого магазин ламається:

- **`max_discount_amount`** — стеля для відсоткових кодів. Без неї «20% на все» на замовленні в 50 000 ₴ дає 10 000 ₴ знижки. Найдорожча відсутня перевірка.
- **`min_order_total`** — мінімальна сума замовлення.
- **`per_customer_limit`** — ліміт на акаунт. Тільки для підтвердженої ідентичності: для гостя `customer_id` порожній, і обмеження не забезпечується.
- **`stackable`** — чи поєднується з іншим кодом. За замовчуванням **ні**.
- **`excludes_discounted_items`** — не застосовувати до позицій, що вже мають `compare_at_price`. Інакше розпродаж плюс код дають продаж нижче собівартості.
- **`excludes_gift_cards`** — за замовчуванням `true`. Інакше сертифікат на 1000 ₴ купується за 800 ₴ і різниця виводиться.
- **`first_order_only`** — код для першої покупки.
- **`description`**, **`created_by_user_id`** — щоб через пів року було зрозуміло, навіщо код існує і хто його зробив.

## 2. Правила валідації

Порядок перевірок у `packages/core/pricing/validate-promo.ts`:

1. Код існує (пошук по `upper(trim(code))`)
2. `is_active = true`
3. `starts_at` настав, `ends_at` не минув
4. `uses_count < max_uses` (якщо `max_uses` задано)
5. Ліміт на клієнта не вичерпаний — тільки для авторизованого
6. `first_order_only`: у клієнта немає попередніх оплачених замовлень
7. Сума кошика ≥ `min_order_total`
8. Область дії: `scope` збігається з наявними позиціями кошика
9. У кошику є хоч одна позиція, до якої код застосовується після
   виключень (`excludes_discounted_items`, `excludes_gift_cards`)

**Нормалізація** — як в оригіналі: uppercase + trim, тому `discount10`,
`DISCOUNT10` і `  discount10  ` — один код.

### Повідомлення про помилки — виправлення безпеки

В оригіналі повідомлення різні: `"Invalid or expired promo code"` проти
`"Promo code usage limit reached"`. Для реєстрації на івенти це нормально,
для магазину — **оракул перебору**: атакуючий за різницею відповідей
визначає, які коди існують, і брутфорсить формати `SUMMER10`, `SALE20`,
`WELCOME15`.

Тому:

- Публічно — **одне** повідомлення: «Промокод недійсний або не застосовується до цього замовлення».
- **Без винятків.** Перша редакція дозволяла конкретику для
  `min_order_total` («додайте товарів на X ₴»). Це той самий оракул:
  відповідь підтверджує, що код існує й застосовний, тому перебір із
  дешевим кошиком відокремлює справжні коди від вигаданих. Походження «з
  вашої розсилки» теж не встановлюється з клієнтського параметра.
  Конкретні умови показуємо лише для кампанії, яку магазин **сам** зробив
  публічною — тобто на сторінці акції, а не у відповіді валідатора.
- Точна причина — у лог із `code`, `ip`, `session`, для аналітики й виявлення перебору.

## 3. Застосування — на кроці розрахунку, не оплати

`POST /api/promo/validate` (route handler) — **лише попередня перевірка для
UI**. Вона нічого не резервує й нічого не гарантує.

Реальне застосування відбувається **всередині транзакції створення
замовлення**, під блокуванням рядка промокоду:

```
BEGIN
  -- Локи в порядку ADR-22: cart → intent → ... → promo_codes → variants
  SELECT * FROM promo_codes WHERE id = $1 FOR UPDATE;
  -- перевірити загальний і клієнтський ліміти ТУТ, не раніше

  -- ПОРЯДОК ВСТАВОК: замовлення ПЕРШЕ.
  -- Перша редакція цього блоку вставляла promo_code_redemptions до orders,
  -- хоча redemption.order_id має NOT NULL FK на ще не створене замовлення.
  -- Відкладених обмежень немає, тому checkout із промокодом падав би на
  -- першому INSERT. Заздалегідь згенерований UUID замовлення рядка не створює.
  INSERT INTO orders ...;
  INSERT INTO order_items ...;          -- зі розподіленим line_discount (ADR-15)
  INSERT INTO promo_code_redemptions (..., state = 'consumed');
  UPDATE promo_codes SET uses_count = uses_count + 1 WHERE id = $1;
  INSERT INTO outbox ...;               -- листи, не пряме надсилання
COMMIT
-- Зовнішні виклики (створення інвойсу) — ПІСЛЯ коміту
```

Те саме правило для сертифікатів: `payment_attempts` створюється **до**
ledger-запису, який на неї посилається.

Без блокування рядка два паралельні оформлення проходять перевірку
останнього доступного використання одночасно. Це не гіпотетично: розсилка
з кодом на 100 використань дає рівно такий трафік.

### Розподіл знижки по позиціях

Знижка зберігається **і** на замовленні (`discount_total`), **і** розкладена
по позиціях (`order_items.line_discount`). Друге обов'язкове: 100 ₴ на три
позиції по 200 ₴ дає 33,33 ₴ на позицію, сума ліній — 99,99 ₴, і одна
копійка розбіжності ламає фіскальний чек та часткове повернення.

Алгоритм — largest remainder: пропорційно з округленням вниз, залишок
копійок до найдорожчої позиції. `packages/core/pricing/allocate-discount.ts`,
unit-тести на нерівномірний поділ, одну позицію, знижку = сумі замовлення.

## 4. Розрахунок ціни

`packages/core/pricing/calculate-cart.ts`. Порядок операцій має значення:

```
1. lineSubtotal      = Σ (unit_price × quantity)
2. eligibleSubtotal  = Σ по позиціях, до яких код застосовується
                       (після excludes_discounted_items, excludes_gift_cards, scope)
3. rawDiscount:
     percent → eligibleSubtotal × value / 100
     fixed   → min(value, eligibleSubtotal)
     free_shipping → 0
4. discount          = min(rawDiscount, max_discount_amount ?? rawDiscount)
5. розподіл discount по eligible-позиціях (largest remainder)
6. shipping          = free_shipping ? 0 : розрахунок перевізника
7. total             = lineSubtotal − discount + shipping + adjustment
```

Ключове порівняно з оригіналом: **знижка рахується від `eligibleSubtotal`, не
від усього кошика.** В оригіналі була одна базова ціна, тут — кошик із
різними позиціями, і код «20% на бюстгальтери» не має чіпати косметику.

`fixed` обмежується `eligibleSubtotal`, тому ціна не буває від'ємною. Це та
сама гарантія, що `Math.max(0, ...)` в оригіналі, але виражена явно.

## 5. Облік використань — відхилення від оригіналу

В оригіналі `usedCount` інкрементується **після успішної оплати**. Для
реєстрації на івенти це працює. Для магазину — ні: два замовлення можуть
створитися з останнім використанням, обидва оплатитися, і ліміт буде
перевищено.

Тут використання **споживається при створенні замовлення** і звільняється,
якщо замовлення не відбулося:

| Подія | Дія |
|---|---|
| Замовлення створено | `redemption.state = 'consumed'`, `uses_count += 1` |
| Оплачено | без змін — уже спожито |
| Скасовано / протерміновано | `state = 'released'`, `released_at`, `uses_count -= 1` |
| Повернення коштів | `state` **не змінюється** — покупка відбулася |

`state` існує саме для того, щоб звільнення відбулося **рівно один раз**.
Без нього воркер expiry й вебхук скасування обидва зменшили б `uses_count`.

Звільнення — умовний перехід, у тій самій транзакції, що й скасування:

```sql
UPDATE promo_code_redemptions
   SET state = 'released', released_at = now()
 WHERE order_id = $1 AND state = 'consumed'
RETURNING id;
```

`uses_count` зменшується **тільки на фактично змінені рядки**.

Воркер `promo:reconcile` щодня звіряє `uses_count` із кількістю redemption
у стані `consumed` і **алертить** про розбіжність, не виправляє тихо.

## 6. Rate limiting

Оригінальні 10 запитів на хвилину на IP лишаються як база, але для магазину
цього мало: код зі знижкою 20% — це реальні гроші, і його варто шукати.

- **10/хв на IP** на `/api/promo/validate`
- **30/год на сесію кошика** — IP ротуються, cart token ні
- **Turnstile** після 5 невдалих спроб у сесії
- Прогресивна затримка: 3 невдачі → +1 с на кожну наступну
- Алерт у Telegram при > 100 невдалих валідацій за 10 хвилин з однієї підсітки

Заголовки `RateLimit-*` — як в оригіналі.

## 7. Адмінка: окрема таба

`/admin/marketing/promo-codes`.

**Список:** код, опис, тип і значення, використано/ліміт (з візуальним
прогресом), період дії, статус, виручка з коду, створив, дата.

- Фільтри: статус (активні / завершені / вичерпані / майбутні), тип, область дії, період створення, «має використання»
- Сортування по кліку на заголовок: код, використання, виручка, дата, дата завершення
- Пошук по коду й опису
- Bulk: деактивувати, продовжити період, експорт CSV

**Форма створення й редагування:**

- Код — з кнопкою генерації (8 символів, без легкоплутаних `0/O`, `1/I/l`)
- Тип, значення, стеля для відсоткових
- Мінімальна сума замовлення
- Ліміти: загальний, на клієнта (з попередженням, що для гостей не працює)
- Область: усі товари / категорія / товар — із пікером
- Перемикачі: `stackable`, `excludes_discounted_items`, `first_order_only`, `excludes_gift_cards`
- Період дії
- **Живий превʼю:** «на кошику 1500 ₴ знижка складе 300 ₴»

Обмеження редагування: у коду з використаннями **не можна змінювати тип,
значення й область** — інакше історичні замовлення стають нез'ясовними.
Можна: продовжити період, підняти ліміт, деактивувати. Це перевіряється в
server action, не лише в UI.

**Статистика коду:** використання в часі, виручка, середній чек із кодом
проти без, кількість нових клієнтів, список замовлень із переходом.

**Ролі:** `content` не має доступу до цієї таби взагалі (промокод — це
гроші). `manager` бачить, не редагує. Створює й редагує `admin` і `owner`.
Кожна зміна — в `audit_log`.

## 8. Що не робимо у v1

- Стековані коди — прапорець `stackable` є в схемі, логіка комбінування ні. Це окремий клубок правил пріоритету
- Персональні одноразові коди на клієнта — після запуску
- Автогенерація кампаній (bulk на 10 000 кодів)
- Коди на безкоштовний товар-подарунок
- Реферальні коди

## 9. Тести — обов'язково

| Сценарій | Чому |
|---|---|
| Два **паралельні** оформлення з останнім використанням | Одне проходить, друге — зрозуміла помилка |
| Скасування двома шляхами одночасно (воркер + вебхук) | `uses_count` зменшується один раз |
| Розподіл 100 ₴ на 3 позиції по 200 ₴ | Сума `line_discount` = 10000 копійок **рівно** |
| Відсоток зі стелею | `min(rawDiscount, max_discount_amount)` |
| `fixed` більший за кошик | Ціна не від'ємна |
| Код на категорію в змішаному кошику | Косметика не подешевшала |
| `excludes_discounted_items` | Позиція з `compare_at_price` не отримала знижки |
| Промокод на сертифікат | Відхилено |
| Повернення коштів | `uses_count` **не** зменшився |
| Однакове повідомлення для «немає» і «вичерпано» | Оракул перебору закритий |
