# ENVIRONMENTS.md

Три середовища: `local`, `staging`, `production`. Обґрунтування — ADR-13.

---

## Матриця

| | local | staging | production |
|---|---|---|---|
| БД | Docker, `pnpm db:seed` | Docker, **анонімізований** дамп прода | Docker, volume + `pg_dump` → R2 |
| Mono / WayForPay | тестові дані + тунель | тестові дані | live |
| Нова Пошта | тестовий ключ | тестовий ключ | live |
| Укрпошта | sandbox | sandbox | live |
| Email | Mailpit у compose, нікуди не виходить | Resend + `EMAIL_TO_OVERRIDE` | реальні відправки |
| Індексація | — | basic auth + `X-Robots-Tag` + `robots.txt` Disallow | відкрито |
| Аналітика | вимкнена | вимкнена | GA4 / Pixel |
| Sentry | вимкнений | окремий проєкт | окремий проєкт |
| `APP_ENV` (серверна!) | `local` | `staging` | `production` |
| Postgres | дефолт | `shared_buffers=128MB` | `shared_buffers=512MB` |

Staging і production живуть на тому ж VPS як окремі compose-проєкти з окремими
volume. Основне обмеження — RAM, тому staging урізаний.

## Локальні вебхуки

Платіжки не можуть стукати на `localhost`. Тунель:

```bash
# NAMED tunnel зі сталим DNS hostname:
cloudflared tunnel create store-dev
cloudflared tunnel route dns store-dev dev.example.com
cloudflared tunnel run store-dev
```

**Виправлення попередньої версії:** там стояло `cloudflared tunnel --url ...`
з твердженням «без ротації домену». Це неправда — така команда створює Quick
Tunnel із **випадковим** піддоменом, який змінюється на кожен запуск. Наслідок
неприємний: провайдер продовжує стукати на стару адресу, а ви шукаєте
проблему в перевірці підпису або в обробнику.

Той самий payload для повторної відправки зберігайте у
`packages/payments/__fixtures__/` — це ж і фікстури для тестів
ідемпотентності.

## Три пастки

### 0. Basic auth блокує callback провайдерів

Найшвидша пастка: браузерний checkout після введення пароля працює, а
провайдер отримує `401` від reverse proxy і навіть не доходить до перевірки
підпису. Запланований end-to-end платіж на staging не проходить, і причина
неочевидна.

З basic auth і будь-яких браузерних challenge виключаються **точні
POST-маршрути** вебхуків — не префікс `/api`, не весь `/api/webhooks`.
На них лишається перевірка підпису, обмеження розміру тіла й журналювання.
Ці маршрути також не проходять через locale- і canonical-редіректи.

Обов'язково: зовнішній тест callback **без** basic auth credentials.

### 1. Staging потрапляє в індекс

Найдорожча помилка. Ви отримуєте повний дубль каталогу на другому домені, і
Google сам вирішує, який вважати основним.

Захист **тришаровий**, одного шару недостатньо:

1. Basic auth на рівні Caddy / Dokploy
2. `X-Robots-Tag: noindex, nofollow` у відповіді
3. `robots.txt` з `Disallow: /`

`robots.txt` окремо не рятує — він забороняє обхід, а не індексацію. URL, на
який є зовнішнє посилання, може потрапити в індекс без обходу.

Перевірка входить у критерії приймання фази 0 **і** фази 12.

### 2. Реальні листи зі staging

Ви розвернули дамп, запустили воркер покинутих кошиків — і кілька сотень людей
отримали лист від тестового стенду.

`EMAIL_TO_OVERRIDE` перекриває **всіх** отримувачів на staging. Це перевіряється
кодом, а не пам'яттю: якщо `APP_ENV !== 'production'` і `EMAIL_TO_OVERRIDE`
не заданий — застосунок падає на старті, а не тихо розсилає.

Перевірка опирається на серверний `APP_ENV`, **не** на `NEXT_PUBLIC_ENV`:
останній вшивається під час build, тому один образ на двох середовищах вважав
би себе production і обійшов захист (ADR-10).

### 3. Персональні дані в дампі — allowlist, не denylist

Попередня версія перелічувала колонки для затирання. Такий підхід **не
працює**: перелік завжди неповний. Він пропускав `orders.comment`,
`orders.admin_note`, `orders.ip`, `orders.user_agent`, `orders.ttn`,
`payment_events.raw_payload` (де телефон і адреса лежать у JSON провайдера),
коментарі та **фотографії** в запитах на повернення, `audit_log.diff` зі
старими значеннями, і відкладені задачі pg-boss із реальними отримувачами.

Тому інверсія: **дозволено лише те, що явно перелічено.**

- Вільний текст, зовнішні payload і вкладені JSON — замінити синтетикою або очистити.
- `auth_*`, `checkout_intents`, `orders.access_token_hash` — видалити повністю.
- Черга pg-boss — очистити: production-задачі на staging не мають виконуватись.
- Фото повернень і відгуків — не переносити.

Санітизована копія створюється в **ізольованому процесі до** того, як staging
отримує доступ. Результат перевіряється контрольними маркерами (шукати
реальні номери телефонів, email-патерни, назви міст) **по всіх таблицях і
всередині JSON**, а не лише по очевидних контактних колонках.

Скрипт — `infra/anonymize.sql`, застосовується **до** імпорту.

## Промоушен staging → production

Порядок має значення. Міграції перед деплоєм коду, якщо вони адитивні;
після — якщо руйнівні (тоді потрібен двофазний реліз).

- [ ] CI зелений: typecheck, lint, unit, e2e
- [ ] `drizzle-kit check` без дрейфу
- [ ] Міграції прогнані на staging з дампом прода — не на seed-даних
- [ ] Міграції перевірені на час виконання: `ALTER TABLE` на великій таблиці блокує
- [ ] Тестовий платіж end-to-end на staging пройшов
- [ ] Тестова ТТН створилась (на тестовому ключі НП)
- [ ] `grep` по `.next/static` не знаходить секретів
- [ ] Snapshot VPS зроблено
- [ ] `pg_dump` виконано вручну перед релізом, файл перевірено
- [ ] Rollback-процедура з `RUNBOOK.md` під рукою
- [ ] Реліз не в п'ятницю ввечері

Після деплою:

- [ ] `/api/health` відповідає
- [ ] Реальний платіж на 1 ₴ і повернення пройшли
- [ ] `curl -A Googlebot` на PDP віддає метадані
- [ ] Sentry не сипле новими помилками 15 хвилин
- [ ] Воркер підхопив cron (перевірити таблицю pg-boss)

## Змінні, специфічні для середовища

Решта — у `.env.example`.

```bash
APP_ENV=staging                  # СЕРВЕРНА, без NEXT_PUBLIC_ (ADR-10)
EMAIL_TO_OVERRIDE=you@mail.com   # обов'язково коли APP_ENV != production
STAGING_BASIC_AUTH_USER=
STAGING_BASIC_AUTH_PASSWORD=
STAGING_BASIC_AUTH_EXCLUDE=/api/webhooks/mono,/api/webhooks/wayforpay
```

Пам'ятайте ADR-10: один Docker-образ їде на staging і production, тому значення,
що мусять читатись у рантаймі, читаються після `await connection()` — і **лише
серверні**, без `NEXT_PUBLIC_`. Інакше staging піде платити live-токеном.

Промоушен перевіряється запуском **того самого image digest** із двома
наборами env, а не двома незалежними білдами.
