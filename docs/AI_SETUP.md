# AI_SETUP.md

Конфігурація AI-інструментів. Claude Code — основний, решта дзеркалиться.

Все з цього файлу входить у **фазу 0**, до першого рядка доменного коду.
Причина проста: агент, який починає працювати без правил, за два дні
створить код, який потім доведеться переписувати під правила.

---

## 1. Джерело істини — `AGENTS.md`, не `CLAUDE.md`

Це головне архітектурне рішення, і воно протилежне тому, з чого ми почали.

`AGENTS.md` — міжвендорна специфікація, яку читають Codex, Cursor, Amp,
Jules і Factory, і яку **Claude Code читає додатково** до `CLAUDE.md`, а не
замість. Тобто дублювати правила у два файли не потрібно й шкідливо: два
описи одного інваріанту розходяться на третьому тижні.

Тому розподіл:

| Файл | Що містить | Хто читає |
|---|---|---|
| **`AGENTS.md`** | **Канон.** Тверді правила, definition of done, режим роботи по фазах, пастки Next.js 16, карта проєкту | усі, включно з Claude Code |
| `CLAUDE.md` | Тільки Claude-специфічне: посилання на субагентів, скіли, хуки, політику permissions. Плюс `@AGENTS.md` на початку | Claude Code |
| дзеркала | генеровані з `AGENTS.md`, не редагуються руками | Copilot, Cursor |

**Міграція наявного `CLAUDE.md`:** його зміст (тверді правила, DoD, §4
пастки Next.js, карта проєкту) переїжджає в `AGENTS.md`. У `CLAUDE.md`
лишається `@AGENTS.md` і Claude-специфічний розділ.

`AGENTS.md` також містить managed-блок від
`npx @next/codemod@canary agents-md` — він вказує агенту на версійно
збігану документацію в `node_modules/next/dist/docs/`. Наш вміст іде
**після** цього блоку, керований блок не чіпаємо.

## 2. Дзеркала й перевірка синхронності

Не всі інструменти читають `AGENTS.md`. Для них — генерація:

```
ai/
├── canonical.md          ← ЄДИНЕ місце, яке редагується руками
└── claude-specific.md
scripts/sync-ai-config.ts ← генерує все нижче
AGENTS.md                 ← managed Next-блок + canonical
CLAUDE.md                 ← @AGENTS.md + claude-specific
.github/copilot-instructions.md
.cursor/rules/project.mdc
```

Кожен згенерований файл починається з:

```
<!-- ЗГЕНЕРОВАНО з ai/canonical.md. Не редагувати. -->
<!-- Правки: ai/canonical.md → pnpm ai:sync -->
```

У CI — джоб `ai-sync`: `pnpm ai:check` порівнює хеші й падає, якщо дзеркала
розійшлися. Без цієї перевірки через місяць у вас три різні версії правил, і
Cursor радить те, що заборонено в Claude Code.

## 3. `.claude/` — структура

```
.claude/
├── settings.json          # у git: правила для команди
├── settings.local.json    # у .gitignore: особисті оверайди
├── skills/                # процедури, які повторюються
│   ├── new-migration/SKILL.md
│   ├── phase-report/SKILL.md
│   ├── money-change/SKILL.md
│   └── new-webhook/SKILL.md
├── agents/                # субагенти з ізольованим контекстом
│   ├── money-reviewer.md
│   ├── migration-reviewer.md
│   ├── security-auditor.md
│   └── seo-reviewer.md
└── hooks/                 # детерміністичні запобіжники
    ├── block-applied-migration.sh
    ├── post-edit-verify.sh
    └── guard-production.sh
```

**Скіли, не команди.** З версії 2.1.101 кастомні slash-команди об'єднані зі
скілами: обидва дають `/name`, і при збігу імен перемагає скіл. Тому
`.claude/commands/` не створюємо — все як скіли, один механізм.

## 4. Скіли

Скіл — це процедура, яку ви інакше повторювали б у промпті щоразу.

### `new-migration`

Найцінніший, бо міграції — найнебезпечніша операція в проєкті.

Що робить: генерує міграцію Drizzle → перевіряє на дангерні DDL (`squawk`) →
**прогонює на порожній БД** через Testcontainers → прогонює на копії
попередньої схеми → якщо міграція ручна (тригери, складені FK), перевіряє,
що вона додана в правильному порядку відносно extensions → показує diff і
чекає підтвердження.

Це закриває три реальні провали з рецензій: `unaccent` у generated-колонці,
extensions після залежних індексів, `ALTER TABLE` із блокуванням.

### `money-change`

Тригериться на зміни в `pricing`, `inventory`, `orders`, `payments`.

Змушує пройти чек-лист перед завершенням: чи всі суми `Money` (не `number`);
чи транзакція передана параметром, а не взята з глобалу; чи є тест на
паралельний виклик; чи сходиться `SUM(line_total + line_discount)` із
`subtotal`; чи зачеплені локи беруться в тому самому порядку.

### `new-webhook`

Порядок операцій із ADR-4 як покроковий чек-лист: raw body до парсингу →
підпис → карантин при невалідному → `FOR UPDATE` на замовленні → вставка
події → перевірка `state_version` → мутації + outbox в одній транзакції →
відповідь через `buildWebhookResponse` **включно з гілкою дубля**.

Плюс обов'язкові тести: дубль ×5, невалідний підпис, порушений порядок,
вебхук раніше за redirect.

### `phase-report`

Формує звіт за формою з `AGENTS.md`: пройдені критерії з посиланням на те,
чим перевірено; непройдені з причиною; відхилення від плану; що потребує
рішення людини. І **не** переходить до наступної фази.

## 5. Субагенти

Субагент має власний контекст, тому не забруднює основну сесію й не
«погоджується» з тим, що сам щойно написав.

| Агент | Викликається | Задача |
|---|---|---|
| `money-reviewer` | перед комітом у `pricing` / `inventory` / `orders` / `payments` | Шукає: округлення поза pricing engine, `number` замість `Money`, глобальний `db` у домені, read-then-write замість умовного `UPDATE`, відсутні тести гонок |
| `migration-reviewer` | на кожну нову міграцію | Блокуючі DDL, порядок extensions, IMMUTABLE у generated-колонках, `ON DELETE` для фінансово значущих таблиць, відсутні індекси під нові запити |
| `security-auditor` | перед завершенням фаз 4, 5, 12 | Перевіряє `SECURITY.md` **прямими запитами в обхід UI**: чи роль справді обмежена в server action, а не лише в UI; чи `cost_price` і `unit_cost_snapshot` не витікають у вкладених читаннях і експортах |
| `seo-reviewer` | фази 1 і 6 | `curl -A Googlebot` на PLP і PDP; наявність title/canonical/hreflang/JSON-LD у первинному HTML; стратегія фасетів; валідність Product і BreadcrumbList |

Ключове: `security-auditor` перевіряє **фактичну серіалізовану відповідь**, а
не те, що видно на екрані. Це третя пастка зі списку — витікає не
`cost_price`, який пам'ятаєш, а `unit_cost_snapshot` у вкладених
`order_items`.

## 6. Хуки — те, що не залежить від «згадає чи ні»

Хуки — це детерміністичні запобіжники. Правило в `AGENTS.md` агент може
пропустити; хук із exit code 2 блокує дію.

```jsonc
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        // Застосовану міграцію правити НЕЛЬЗЯ — тільки нова.
        // Інакше drizzle-kit і продакшн розходяться назавжди.
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/block-applied-migration.sh" }]
      },
      {
        // .env продакшену, реальний платіж, реальна ТТН, DDL на проді
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": ".claude/hooks/guard-production.sh" }]
      }
    ],
    "PostToolUse": [
      {
        // Автоформат + лінт відразу після правки: агент не накопичує
        // 40 файлів, які потім усі разом не проходять CI
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/post-edit-verify.sh" }]
      }
    ],
    "Stop": [
      {
        // Не завершувати хід із червоним typecheck
        "hooks": [{ "type": "command", "command": "pnpm turbo typecheck" }]
      }
    ]
  },
  "permissions": {
    "allow": ["Bash(pnpm *)", "Bash(git diff *)", "Bash(git status)", "Read", "Grep", "Glob"],
    "deny": [
      "Bash(git push --force*)",
      "Bash(psql *production*)",
      "Bash(drizzle-kit push*)",
      "Read(./.env)",
      "Read(./.env.production)"
    ]
  }
}
```

`drizzle-kit push` у deny свідомо: воно змінює схему без файлу міграції,
тобто локально «працює», а в продакшн нічого не доїжджає.

Перелік hook-подій у Claude Code значно ширший за ці чотири (є
`SessionStart`, `SubagentStop`, `PreCompact` та інші) — але починати варто з
мінімуму, який реально ловить помилки. Актуальний перелік дивіться в
документації, він розширюється.

## 7. MCP

У проєкті доречні три:

- **Postgres (read-only)** — щоб агент дивився фактичну схему замість
  припущень із `schema.ts`. Обов'язково read-only і **тільки** до локальної
  або staging БД.
- **Playwright** — щоб перевіряти власну роботу в браузері, а не питати вас,
  чи працює.
- **Context7** або аналог — актуальна документація Next.js 16, Drizzle,
  Auth.js. Це прямо закриває головний ризик: у 16 багато API розійшлися з
  тим, що модель «знає» з тренування.

Продакшн-БД до MCP не підключається. Ніколи.

## 8. Що НЕ робимо

- **Не дозволяємо агенту автокоміт і автопуш.** Ревʼю diff — точка, де
  ловиться більшість проблем.
- **Не даємо доступу до продакшн-секретів.** `.env.production` у deny.
- **Не тримаємо правила у трьох місцях руками.** Одне джерело, генерація,
  перевірка в CI.
- **Не пишемо в `AGENTS.md` те, що можна перевірити лінтером.** «Ніяких
  `any`» у прозі — побажання; `no-unsafe-assignment: error` — інваріант.
  Правило в промпті потрібне лише там, де автоматична перевірка неможлива.

хуком або тестом. Якщо можна — робіть так, а не текстом.
